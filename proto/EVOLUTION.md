# Evolving the proto contract

The rules for changing anything under `proto/`, and the reasoning behind
them. `buf breaking` enforces the mechanical half in CI; the rest is
judgement this file exists to inform.

The governing idea, from the architecture doc:

> The gateway container can wait. The contract cannot.

Web, mobile and third parties are all intended clients of this system. The
first two can be refactored alongside a change here. The third cannot: a
partner's integration is code you do not own, cannot see, and cannot fix.
Every rule below is about the moment that becomes true, which is not yet,
which is exactly why the rules are cheap to adopt today.

## The rules

**1. `v1` evolves additively. Nothing else.**

Add fields, add messages, add RPCs. Never remove, never renumber, never
change a type. A breaking change means a new package version (`v2`
alongside `v1`), never an edit to the one people already call.

**2. Removed fields get `reserved` tags, always.**

```proto
message Membership {
  reserved 4;
  reserved "legacy_role";

  string org_id = 1;
  string org_name = 2;
  string role = 3;
}
```

Reserving is what stops tag 4 being handed to a different field later. A
client compiled against the old contract would decode the new field into
the old one and be wrong in silence rather than loudly, which is the worst
available failure: no error, wrong data, and the wrong system blamed.

`buf breaking` catches a reused tag. It cannot catch a tag you removed
today and reuse in two years unless the reservation is written down, so
reserving is the habit rather than the fallback.

**3. Every RPC declares its REST binding and its required scope.**

Two method options, both enforced by reflection tests that name the
offending method:

```proto
rpc GetCurrentUser(GetCurrentUserRequest) returns (GetCurrentUserResponse) {
  option (kindlast.options.v1.required_scope) = "openid";
  option (google.api.http) = {get: "/api/v1/me"};
}
```

A method missing the scope is reachable with any valid token. A method
missing the binding is absent from the OpenAPI document, and therefore
from every generated client, while appearing to exist. Neither failure
announces itself, which is why both are tests rather than conventions.

**4. Paths follow `/api/v1/...`, with `:verb` for custom actions.**

`POST /api/v1/invitations/{token}:accept`, per AIP-136, not
`/invitations/{token}/accept`, which reads as a subresource that does not
exist.

**5. The generated OpenAPI document is committed.**

`gen/openapi/openapi.yaml`, regenerated by `buf generate` and covered by
the CI drift check. It is generated from the same annotations that route
requests, so the document and the behaviour cannot disagree. Hand-editing
it is always wrong; change the proto.

## What `buf breaking` does and does not catch

Configured with `FILE` in `buf.yaml`, compared against `main`.

It catches: deleted fields, messages, enums and RPCs; changed field types;
reused tags; renamed fields; changed cardinality.

It does not catch: a semantic change that keeps the shape. Repurposing
`role` from `owner|member|viewer` to something else passes every check and
breaks every caller. A comment is not enough for that; add a field and
deprecate the old one.

It also does not catch a tag reused after a long enough gap, which is what
rule 2 is for.

## Deprecating rather than removing

```proto
string legacy_role = 4 [deprecated = true];
```

The field stays, the annotation marks it, generated clients warn. Removal
waits for a published sunset window, which is ENT-193 sub-issue 4 and does
not exist yet. Until it does, **nothing is removed from `v1`**.
